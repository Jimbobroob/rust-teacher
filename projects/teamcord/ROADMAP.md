# TeamCord: roadmap

A roadmap, not a spec. The learner decides everything; the teacher recommends. Update it when decisions change. It is the plan, not progress: progress lives in `log/` in `rust-learning/`, and the day-by-day tracking in `CHECKLIST.md`.

Repo: `~/source/repos/TeamCord/` (GitHub org `TeamCoMedia`). The same path on their laptop.

## What it is

A Discord-style chat app that runs locally and in the cloud, like TeamSpeak but polished. Text messages first; voice and other features later. One installation hosts a whole platform where one person can create as many servers as they want; the installation itself starts with one server. Eventually a setup wizard or installer sets up a local server, instead of typed commands (late stage, details later).

First audience: the learner and one friend, then a couple of test users. Not a public service yet.

## Starting point

- Backend: a small C# ASP.NET project (`src/TeamCord.BFF`): one controller, one SignalR hub, one message service, a messages model, EF Core against Postgres. Far from finished. It is deleted once the Rust server does stage 1 end to end with the front end.
- Front end: Next.js 16, React 19, TypeScript, Tailwind, shadcn/ui, with a chat page and a SignalR client (`src/tsapp`).
- `infra/docker/docker-compose.yml`: front end, backend, Postgres 18.
- `docs/` describes an older design in C with SQLite that never matched the code. The learner will write new docs themselves later; not a roadmap task.

## Stack

Rust (`axum`, `tokio`, `sqlx`, `serde`, `tracing`), Postgres, Next.js and TypeScript, Docker and Docker Compose. Modules for the non-Rust parts are in `modules/`. No Kubernetes, no Terraform, no new CI for now. Crate names here are from memory; check them when they come up.

## Decisions (the learner's, with the teacher's reasons)

- **Rewrite in place, then delete the C#:** the Rust server is a new crate beside the C# one, on a branch, and the C# goes once Rust covers stage 1. Git history keeps the old code.
- **One person can create many servers.** A server is a row; members and channels belong to it.
- **Transport:** a plain WebSocket carrying MessagePack messages with explicit types and a version field, plus normal HTTP for login and history. SignalR goes because its protocol is its own and isn't practical to rebuild in Rust. The TypeScript message types are hand-written at first and checked at runtime; generating them from the Rust types is an option later.
- **Rust layout:** a Cargo workspace in `src/` with a `server` binary crate and a `protocol` library crate for the message types. May change.
- **Database:** `sqlx` with plain SQL migrations and no ORM. Tests run against a real Postgres in Docker.
- **IDs:** UUIDv7, generated by the application.
- **Delivery:** the server assigns the message ID and timestamp and acknowledges the sender. The client sends its own temporary ID so a retry isn't a duplicate. A friend who is offline sees the message in history on next open. No push notifications.
- **Auth (stage 2):** sign-up by invite code only (single-use, with expiry). Argon2id password hashes. An opaque session token stored in Postgres and sent in an HttpOnly, Secure, SameSite cookie. The WebSocket connects with a single-use ticket fetched over authenticated HTTP, and the server checks `Origin`. Login rate limiting and temporary lockout, logout and a list of active sessions that can be revoked, password change, a log of auth events. Password reset is by an admin from the command line. Two-factor (TOTP) and passkeys are later.
- **Friends (stage 4):** mutual. One person sends a request, the other accepts. You can only DM a friend. You find people by exact username.
- **Presence and typing indicators:** after servers.
- **Testing and logging from stage 1:** unit tests for message encoding and decoding, integration tests against Postgres in Docker, structured logs with `tracing`.
- **Open:** how the friend reaches the server in stage 3 (see that stage). Decide it after talking to them.

## Constraints

- Cost: they cannot pay large bills. Check a price on the provider's own page before creating anything, and never leave resources running unmonitored.
- Pace: about 2 hours a day, with more done during the three weeks of holiday next month. No deadline; quality and understanding come first, and nothing is cut to hit a date.
- The code is theirs. Concepts, tooling commands and design recommendations are taught; solutions are not given.

## Stages

Each stage ends with something they can run and show. Topic numbers are from `curriculum.md`; the teacher warns about the likely ones at the start of each task and teaches properly when they hit them, per "Just in time" in `SKILL.md`.

### Stage 0: foundations from TeamCord's own shapes

- **Exists at the end:** a small offline Rust program that models chat messages and users, with validation and tests. No network and no database. It replaces the old plan for `change-finder`.
- **Topics:** 1 to 7, 10; 3 and 4 are the long ones.
- **Risks:** ownership and borrowing errors arrive early and in volume; the unfinished carried-forward items from `syntax-time-split` (see `log/overview.md`).

### Stage 1: messages, running locally

- **Exists at the end:** a Rust server that lets two browser tabs, as two people, send each other direct messages live, saved in Postgres and loaded as history. Identity is a user ID chosen with a dev-only picker, with no passwords. The Next.js app uses a WebSocket client instead of SignalR. `docker compose up` starts it all. The C# backend is deleted.
- **Parts:** workspace and `protocol` crate; MessagePack with `serde`; `axum` WebSocket handling; users, conversations and messages tables with UUIDv7 IDs and migrations; message acknowledgement and retry-safe IDs; fan-out to connected clients; tests and `tracing`; the front end client and its runtime checks; the Docker Compose change.
- **Topics:** 8, 9, 11, 13, 15, 16, 18, 19, 21, 22; modules for Docker, TypeScript and React, SQL and Postgres, API design.
- **Risks:** async and holding locks across `.await`; sharing connection state between tasks (`Arc` and `Mutex` costs); slow clients and backpressure; WebSocket reconnects; keeping the TypeScript types in step with the Rust ones; the user-ID design, so stage 2 swaps the picker for real login without reworking the protocol.

### Stage 2: real auth

- **Exists at the end:** invite-only accounts with login, sessions and the checklist in Decisions. No unauthenticated access to anything except login and sign-up.
- **Topics:** 6 and 17 (errors at boundaries), 20 (middleware), 21 (transactions), 22, 24.
- **Risks:** cross-site WebSocket hijacking and CSRF; cookie flags and cross-origin dev setup (`localhost:3000` to `localhost:8080`); password and token handling in logs; getting rate limiting wrong in a way that locks out real users.

### Stage 3: reaching it across the web

- **Exists at the end:** the learner's friend uses it from their own machine.
- **Options, decide later with the friend:** a private network tool such as Tailscale, which exposes nothing publicly; a tunnel such as Cloudflare Tunnel or ngrok, which gives a public URL; a small rented server running Docker Compose with a domain and HTTPS through a reverse proxy such as Caddy; opening a home router port, which is advised against. Prices and free tiers are not checked here; check each before choosing.
- **Topics:** 24; Docker module.
- **Risks:** HTTPS and secure cookies behind a proxy; cost of a rented server and anything that bills after it is deleted.

### Stage 4: friends list

- **Exists at the end:** requests, accepting and declining, listing friends, and DMs only between friends.
- **Topics:** 21 (schema design in the SQL module), 19.
- **Risks:** a symmetric relationship in a table (duplicate or crossed requests); who may see whom.

### Stage 5: servers and channels

- **Exists at the end:** a person can create servers, invite people, and create channels with messages in them.
- **Topics:** 21, 22, 17; roles and permissions come as a later step.
- **Risks:** every query has to be scoped to a server; authorization on every action.

### Later (unordered)

Presence and typing indicators; voice (WebRTC, a large topic of its own); the setup wizard or installer; two-factor and passkeys; roles and permissions; message edits, deletes and reactions; file uploads; search; performance testing (23).
